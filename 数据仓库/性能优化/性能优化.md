# 业务优化原则
核心：减少计算量，从业务角度出发，考虑是否可以复用表或者算一次多用，避免重复计算

## 读数据优化
- 充分利用分区条件减少文件扫描量
- 适当大小的文件以减少单个task处理的数据量
- 高效存储格式（parquet、orc等）提升IO速度和避免不必要的数据读取
- 缓存或临时表以减少多次大表扫描
- 使用可分割的文件压缩方法，比如zlib，zstd等压缩算法，避免gzip、zip

## 写数据优化
- 消除小文件生成以减少文件操作开销—非常关键，尽量保证与文件块大小保证一致，默认128M
- 动态分区写入数据以避免串行写入

## 计算优化
- 去重后再join，减少膨胀
- 去除无意义的代码（如在写入操作的末尾加OrderBy）
- 申请更多资源并提高partition的并发度
- 避免非等值join和笛卡尔积join，否则性能不理想

# 通用参数优化
## Shuffle并发优化
Spark ui图中可以看出shuffle read大小为256M左右，每个task处理的shuffle数据量过大，shuffle默认并发为200
<img width="1108" height="540" alt="image" src="https://github.com/user-attachments/assets/6324406c-939a-4314-a15b-6fc2a2c983ee" />


1）手动设置shuffle并发优化
手动增加shuffle并发数，通过设置spark.sql.shuffle.partitions=400

2）自适应shuffle并发优化
SparkSQL自适应框架可以通过设置shuffle partition的上下限区间，在这个区间内对不同作业不同阶段的reduce个数进行动态调整。通过区间的设置，一方面可以大大减少调优的成本（不需要找到一个固定值），另一方面同一个作业内部不同reduce阶段的reduce个数也能动态调整，通过设置：
spark.sql.adaptive.enabled=true \
spark.sql.adaptive.shuffle.targetPostShuffleInputSize=128000000 \

|属性名称|默认值|备注|
| ---- | ---- | ---- |
|spark.sql.adaptive.enabled|false|自适应执行框架的开关。|
|spark.sql.adaptive.minNumPostShufflePartitions|1|reduce个数区间最小值。|
|spark.sql.adaptive.maxNumPostShufflePartitions|500|reduce个数区间最大值。|
|spark.sql.adaptive.shuffle.targetPostShuffleInputSize|67108864|动态调整reduce个数的partition大小依据，如设置64MB，则reduce阶段每个task最少处理64MB的数据。|
|spark.sql.adaptive.shuffle.targetPostShuffleRowCount|20000000|动态调整reduce个数的partition条数依据，如设置20000000则reduce阶段每个task最少处理20000000条的数据。|

## Spark join优化
通过Spark ui查看sql运行过程中join语法最终所选择的join类型，性能优先级为：Broadcast Hash Join > Sort Merge Join > Shuffle Hash Join > cartesian Join > Broadcast Nested Loop Join.

场景一：大表join小表，此时一定要转换成性能最佳的BroadcastHashJoin，通过设置小表阈值spark.sql.autoBroadcastJoinThreshold=200000000，根据小表实际大小设置，建议不要超过2G，避免driver端出现oom溢出
<img width="788" height="739" alt="image" src="https://github.com/user-attachments/assets/4bd5a722-a2e4-4356-8b17-147e8242f157" />


场景二：大表join大表，大表无法满足spark.sql.autoBroadcastJoinThreshold阈值，则会自动转换成SortMergeJoin，性能略差BroadcastHashJoin，注意考虑数据倾斜

注意：
1、join语句一定要加on字段条件和等值条件，否则将会变成性能最差的Broadcast Nested Loop Join和cartesian Join，此时只能通过增加shuffle并发来提升处理性能spark.sql.shuffle.partitions=400

业务优化：数据倾斜一般是某个字段的值过多导致，在SQL改造上可以通过识别出倾斜字段值，通过单独子查询处理，然后union剩下字段值，做业务拆分

场景一：join语法中生成的SortMergeJoin导致的shuffle过程数据倾斜，可以通过AQE方式处理倾斜join，也可以转换成BroadcastHashJoin，避免shuffle过程
spark.sql.adaptive.forceOptimizeSkewedJoin=true

spark.sql.adaptive.skewJoin.skewedPartitionFactor=1

spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes=64MB

spark.sql.adaptive.skewJoin.optimizeGeneralJoins=true

spark.sql.adaptive.enabled=true

spark.sql.autoBroadcastJoinThreshold=200000000

spark.sql.adaptive.skewJoin.optimizeMultiTableJoins=true

样例优化参考：
```sql
--广播小表
select /*+ BROADCAST (table1) */ * from table1 join table2 on table1.id = table2.id

--分离倾斜数据（倾斜key已知）
select * from table1_1 join table2 on table1_1.id = table2.id
union all
select /*+ BROADCAST (table1_2) */ * from table1_2 join table2 on table1_2.id = table2.id

--打散数据（倾斜key未知）
select id, value, concat(id, (rand() * 10000) % 3) as new_id from A

select id, value, concat(id, suffix) as new_id
from ( 
      select id, value, suffix
      from B Lateral View explode(array(0, 1, 2)) tmp as suffix
)

--打散数据（倾斜key已知）
select t1.id, t1.id_rand, t2.name
  from (
        select id ,
               case when id = null then concat(‘SkewData_’, cast(rand() as string))
                    else id end as id_rand
          from test1
          where statis_date = ‘20200703’) t1
  left join test2 t2
    on t1.id_rand = t2.id 
```

同时，适度增大spark.sql.shuffle.partitions参数，通过提高并发度的方式也可缓解数据倾斜。

# 特定场景优化
## not in子查询优化
适用场景：查看作业中是不是用not in（select），如果有，同时spark ui执行计划图里面存在broadCastNestedLoopJoin，对左右两表的数据进行笛卡尔积运算，此时性能会非常差，建议修改为Not exists语法，或者利用not in自动转Not exists特性
spark.sql.optimizeNullAwareAntiJoin=true
spark.sql.optimizeSingleColumnNotIn=true

## count distinct优化
适用场景：作业中包含多个count distinct，如果是则添加如下优化参数：
spark.sql.expand.pullup=true
spark.sql.expand.merge=true
spark.sql.expand.filter=true
spark.sql.expand.keepAggregate=true

## SortMergeJoin优化
适用场景：重新执行作业，如果发现作业中有一些SortMerge join，但是有一边的data size较少（小于40M）或者有明显倾斜的场景，就将AE打开
spark.sql.autoBroadcastJoinThreshold = 20000000
spark.sql.adaptive.enabled = true

## get_json_object复用优化
适用场景：如果sql中有多个get_json_object(obj, $.name)，增加如下参数优化
spark.sql.jsonExpression.reuseJsonParsingEnabled=true
spark.sql.jsonExpression.reuseJsonParsingThreshold=3

## HashAggregate skip优化
适用场景：如果发现partial HashAggregate后的数据量聚合效果一般，则可以利用skip partial agg优化
spark.sql.aggregate.adaptivePartialAggregationEnabled=true
spark.sql.aggregate.adaptivePartialAggregationThreshold=100000
spark.sql.aggregate.adaptivePartialAggregationRatio=0.5

## 窗口函数优化
适用场景：如果sql语句中有窗口函数，且由于在窗口函数中没有partition by则会导致singlePartition慢的问题
spark.sql.repartition.agg=true
spark.sql.repartition.agg.partial=true

## 表重用
适用场景：如果发现web UI中有大量的重复计算，如同一张表被scan多次等，可以尝试利用Subquery Fusion技术
spark.sql.subQueryFusion.enabled=true
spark.sql.subQueryFusion.union.elimination.enabled=true
spark.sql.subQueryFusion.introduce.exchange.enabled=true
spark.sql.subQueryFusion.pullupWindow.enabled=true
