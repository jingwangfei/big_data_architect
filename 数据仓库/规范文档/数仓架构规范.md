## 一、数据分层架构
### 1.1 分层架构图
<img width="1236" height="884" alt="image" src="https://github.com/user-attachments/assets/9528d2fc-33dd-4ecc-a697-2dd8546e8139" />

核心分层：`ODS (Operation Data Store)` → `DWD (Data Warehouse Detail)` → `DWS (Data Warehouse Summary)` → `APP (Application Data Layer)`，配套维度层 `DIM (Dimension)`  
分层数据流向：  
业务应用（报表、运营）→ APP层（各种指标、cube数据）→ DWS层（轻度汇总数据）→ DWD层 → ODS层（DSP、ADX、DMP、LUNA前端埋点、Creative等数据源）  
（注：DIM层为独立维度层，支撑DWD、DWS、APP层的维度需求）


### 1.2 层架调用原则
设计目标：避免烟囱式建设，提升数据共享度，减少重复计算，保障数据一致性。  
核心规则：  
- ODS层：仅允许被DWD层调用，**禁止跨层调用**（如APP层直接调用ODS层）。  
- DWD层：主要依赖ODS层，尽量不依赖其他DWD表，减少层内耦合。  
- DWS层：层级不宜过深（建议不超过5层）；优先沉淀常用指标，避免APP层过度回查DWD层。  
- APP层：优先调用DWS层和DWD层数据，**禁止依赖ODS层或APP层自身**。  


### 各分层设计原则
#### 1. ODS (Operation Data Store)
- 数据源范围：接收多源数据，包括流量日志、业务日志、业务数据、API第三方数据。  
- 数据一致性：数据及字段结构与源系统保持一致，不做额外加工。  


#### 2. DWD (Data Warehouse Detail)
- 数据组织：按业务主题划分明细数据，产出格式统一、质量可靠的业务明细层数据。  
- 建模规范：遵从维度建模，**优先采用星形模型**，少用雪花模型；允许维度冗余以提升查询效率。  
- 数据粒度：原子级业务事实数据，必须为事实表。  
- 层级依赖：主要依赖ODS层，少依赖其他DWD表，**禁止依赖DWS层**；理论上每张ODS表需对应1张或多张DWD表。  
- 主题划分：按《数据标准规范》中“现有业务主题划分”执行。  


#### 3. DWS (Data Warehouse Summary)
- 数据定位：按业务需求进行轻度汇总，产出通用、稳定的预处理数据，减少后续重复计算。  
- 汇总粒度：轻度汇总（如“用户维度的浏览/点击/电话行为汇总”）。  
- 层级依赖：主要依赖DWD层和DIM层，尽量少依赖其他DWS表，**禁止依赖ODS层和APP层**。  
- 主题归属：不强制划分主题，但需归属到DWS对应主题库，通过表名区分（参考《数据标准规范》）。  
- 指标要求：  
  - 必须包含基础常用指标，定义清晰且不频繁变动；  
  - 涵盖“DWD层直接统计的指标”（如count、sum、distinct计算）和“常用分析型指标”（如基于算法的转化指标）；  
  - 参考《数据标准规范 - 指标命名规范》。  
- 维度处理：可适当冗余维度属性以简化计算。  


#### 4. APP (Application Data Layer)
- 数据定位：高度汇总数据，统一指标计算口径和方法，避免指标冗余计算导致的不一致。  
- 汇总粒度：高度汇总（如“业务线维度的月度核心指标汇总”）。  
- 层级依赖：主要依赖DWS层和DWD层，**禁止依赖ODS层和APP层自身**。  
- 主题划分：基于指标类型进行主题拆分。  
- 维度处理：按“稳定维度”和“不稳定维度”拆分维度表。  
- 指标限制：  
  - 可累加指标（如PV）：控制在15个以内；  
  - 不可累加指标（如UV）：控制在5个以内（需按cube组合运算，避免复杂度过高）；  
  - 不包含衍生指标。  


#### 5. DIM (Dimension)
- 维度定位：提供分析视角的维度数据，需具备“丰富属性”“历史可追溯性”“一致性”，避免维度二义性。  
- 维度分类：  
  - 常量维度：如省份/城市信息、手工录入维度、业务原始表中的基础属性（如创作者基础属性）；  
  - 计算维度：通过条件判断、汇总等逻辑生成的维度（如“用户活跃度等级维度”）。  
- 核心规则：  
  1. 维度组成：包含主键（标识维度粒度）和描述信息；  
  2. 维度粒度：支持细化到“内容、视频、用户”等最小分析单元；  
  3. 层级依赖：可依赖ODS层和DWD层；  
  4. 数据同步：一般每日全量抽取，保持与前端业务同步；每日同步MySQL数据至新分区，保障历史可追溯。  


## 二、维度建模规范
维度建模是数仓建设核心，需通过“**总线架构**”汇聚各业务板块数据（如论坛、博客、学院、下载、问答、VIP会员），避免数据孤岛。

### 核心步骤
<img width="1158" height="684" alt="image" src="https://github.com/user-attachments/assets/1c632bf8-7861-4ff7-b833-69897f4740a3" />

1. 选择业务过程：明确建模对应的业务场景（如“用户下单”“视频播放”）；  
2. 声明粒度：定义事实表的最小分析单元（如“每笔订单”“每一次播放”）；  
3. 确定维度：梳理分析视角（如“时间维度、用户维度、商品维度”）；  
4. 确定事实：提取业务过程中的度量值（如“订单金额、播放时长”）；  
5. 文档落地：通过“总线矩阵”描述业务流程，输出《总线矩阵文档》。


### 2.1 维度表设计
维度表处理占建模工作量的80%以上，是总线架构的核心，需在全企业范围内保持维度一致性。  
建模选型：**采用星形模型**，通过冗余数据提升OLAP查询性能和灵活性。


#### 2.1.1 维度设计原则
1. **一致性准则**：企业级范围内构建统一共享维度，交叉业务场景的维度需完全一致；  
2. **避免雪花模型**：OLAP系统无需频繁变更数据，优先考虑使用成本和性能，不推荐范式化的雪花模型；  
3. **缓慢变化维度处理**：通过日快照维表记录历史变化，尽量避免拉链表（受分区、性能限制）；  
4. **层次维度扁平化**：将层级结构（如“国家-省份-城市”）扁平化存储，简化查询。


#### 2.1.3 缓慢变化维度（SCD）处理方案
根据“是否需记录历史”“数据规模”“更新频率”选择以下方案：  
| 方案类型       | 适用场景                                  | 实现方式                          |
|----------------|-------------------------------------------|-----------------------------------|
| 覆写维度表     | 不关心历史数据、非分区表                  | 每日全量覆盖原有数据              |
| 快照维度表     | 需记录历史、数据规模较小、分区表          | 按日分区存储，保留每日维度快照    |
| 历史拉链表     | 需记录历史、数据规模较大、分区表          | 非分区表本质，可设分区提升查询性能|


### 2.2 事实表设计
事实表由“维度关联字段”和“度量字段”组成，一行数据对应一个业务过程的最小粒度。


#### 2.2.1 事实表分类
（原文未明确分类内容，建议参考《数据标准规范》补充，如原子事实表、汇总事实表、事务事实表、快照事实表等）


#### 2.2.1 事实设计原则
1. **边界原则**：仅选择与当前业务过程直接相关的事实，避免冗余；  
2. **最细粒度原则**：精确定义每行数据的业务含义，优先选择原子粒度（如“每笔订单明细”而非“每日订单汇总”）；  
3. **维度退化原则**：反规范化处理，将常用维度属性（如“商品类别名称”）冗余到事实表，减少表关联；  
4. **单/多事务事实表选择**：若多个业务过程的“粒度相同、维度一致”，可合并为多事务事实表（如“用户下单+支付”合并存储）。


## 三、命名规范
目标：提升数据可读性和可维护性，确保团队认知一致。


### 1. 表名
- 要求：使用有意义的名称，准确反映表内容，避免模糊缩写；  
- 格式：下划线命名法（如`customer_order`，表示“客户订单表”）；  
- 补充：视图名遵循同表名规则。


### 2. 列名
- 要求：简洁明了，准确描述字段含义，避免无意义名称（如`col1`）或过长名称；  
- 格式：下划线命名法或驼峰命名法（如`order_date`或`orderDate`）。


### 3. 主键与外键
- 主键：命名格式为“表名 + _id”（如`customer_id`“product_id”），标识表的唯一粒度；  
- 外键：与关联表的主键同名（如订单表的`customer_id`关联客户表的`customer_id`）。


### 4. 时间相关字段
- 粒度清晰：名称需包含时间粒度（如`order_date`“created_at”“monthly_revenue”）；  
- 周期标识：周期类字段需明确周期（如`quarterly_sales`表示“季度销售额”）。


### 5. 编码规则
- 一致性：代码/标识符采用统一规则（如大写字母+下划线）；  
- 可读性：编码需具备描述性（如`USER_TYPE_01`表示“用户类型-普通用户”，而非`UT01`）。


### 6. 避免关键字
禁止使用数据库系统（如Hive、MySQL）或编程语言的关键字作为表名、列名、视图名（如`order`“user”）。


### 7. 注释与文档
- 要求：为表、视图、列提供清晰注释，说明“数据含义、业务用途、计算逻辑”；  
- 参考：维度表/事实表及字段的注释需对齐《数据标准规范》，便于业务用户理解。


## 四、数据质量规范
详细规则参考《数据质量规范》，核心包含“数据目标-保障-评估”和“数据存储”两大体系。


### 1. 数据目标_保障_评估（数据治理保障评估体系）
<img width="1126" height="584" alt="image" src="https://github.com/user-attachments/assets/8f1bae55-b9c8-4204-82c3-f826b3acafe1" />

| 核心目标 | 保障方案                | 评估规则                                  |
|----------|-------------------------|-------------------------------------------|
| 及时     | 及时性保障机制          | 超时任务扣分、破线任务扣分                |
| 准确     | 数据校验（DQC）         | 字段超长任务扣分、数据质量分量化评估      |
| 完整     | 完整性校验规则          | 新增校验配置加分、未配置校验规则扣分      |
| 有效     | 有效性校验（强/弱规则） | 自定义规则校验，不符合规则数据标记        |
| 一致     | 一致性校验机制          | 跨表/跨层数据一致性比对，不一致数据告警    |


### 2. 数据存储（存储治理评估体系）
<img width="1766" height="840" alt="image" src="https://github.com/user-attachments/assets/57ef43df-a873-43a2-ba9d-503ad898c349" />

- 治理目标：降低存储成本、缩短取数周期、提升人效，保障数据质量且不影响使用效率；  
- 评估规则：  
  - 规范性扣分：存在孤立数据/孤立路径、空表/空分区；  
  - 基础分数：新表创建30天内默认100分、基础层数据默认100分、白名单表默认100分；  
- 治理维度：存储质量、存储规范、人员操作合规性。
