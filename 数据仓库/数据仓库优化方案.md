# 数据仓库系统优化方案（初版）

本文档是21年，提出的对现有数仓的优化方案。


## 一、现有问题
目前，数据仓库系统在使用过程中暴露出诸多设计不足，具体如下：

### 1. 数据建模
现有数仓模型建设未采用规范化的建模方法论（如维度建模、总线架构等），导致：
- 数仓分层（如ODS、DWD、DWS等）界限模糊，层级职责不清晰；
- 维度模型混乱，缺乏统一的设计标准，各业务线数据孤立形成“数据孤岛”；
- 未建立统一的维度表、事实表及指标体系，数据复用性低；
- 缺乏配套的落地文档（如模型设计文档、字段说明等），导致系统维护和迭代困难。


### 2. 规范缺失
#### （1）逻辑设计阶段
- 表名称、字段名称未遵循统一规范，表名混乱，无法通过名称直观判断表的用途；
- 部分字段命名使用数据库关键字（如`order`、`user`等），导致SQL执行异常；
- 同一维度、事实或指标的命名存在不一致（如“用户数”同时存在`user_cnt`、`cust_num`等）。

#### （2）物理设计阶段
- 未考虑部分表的生命周期（如临时表未设置自动清理规则），导致存储资源浪费；
- 分区字段设计不合理，未适当使用二级分区（如时间分区+业务类型分区），影响查询性能；
- 表和字段缺乏注释，新人接手或跨团队协作时理解成本高。

#### （3）ETL过程
- SQL编写未遵循统一规则：关键字大小写混用（如`Select`、`WHERE`）、子查询嵌套超过3层导致可读性差；
- `WITH AS`子句别名随意（如`a`、`temp`等无意义别名），逻辑难以追溯；
- 缺乏关键性注释（如计算逻辑、过滤条件的业务背景），维护困难。


### 3. 数据安全与质量
- 缺乏数据质量监控机制，核心字段（如订单金额、用户ID）未设置验证规则（如非空、范围校验等）；
- 数据安全管控不足，未明确核心数据的脱敏规则和访问权限层级。


## 二、优化愿景
通过本次优化，建立规范的数仓流程、设计标准及落地文档，实现以下目标：

- **数仓体系**：高内聚（各层级职责明确）、低耦合（减少表间不必要依赖）、避免重复计算；具备高性能（支持快速查询）和高扩展性（适应业务快速迭代）。
- **数据质量**：实现需求指标治理（统一指标口径）、建立全链路数据质量监控（异常及时预警）。
- **数据安全**：落实数据脱敏（如手机号、身份证号部分隐藏）、实现层级/表/字段级别的安全验证（如敏感字段仅授权用户可访问）。


## 三、实施步骤
本次实施按数仓开发全流程推进，核心包含需求分析、维度建模、物理设计、ETL设计与开发四个阶段。

#### （4）指标命名规则
<img width="1220" height="322" alt="image" src="https://github.com/user-attachments/assets/108d8893-8c63-4705-a84a-e34b910f28a5" />

指标名称结构：`业务主题-限制条件-计算维度-指标名称`  
- 业务主题：指标应用的业务范围（如“博客”“订单”）；
- 限制条件：指标计算的必要条件（交集用“-”，并集用“&”，如“剔除爬虫-登录用户”）；
- 计算维度：指标切分的维度（如“城市”“时段”）；
- 指标名称：简洁描述指标含义（如“留存率”“转化率”）。

**规则补充**：  
- 非必要结构可省略（如默认维度可隐去），形成“主题-名称”简写；
- 名称过长时（如数据产品开发），可仅保留名称，业务主题以注释补充。

**示例**：  
- 全称：`博客-登录-发博-全维度-留存率`  
- 简写：`博客-发博-留存率`（省略默认的“全维度”）  


### 3. 维度建模
维度建模是数仓建设的核心，包含4个步骤：`选择业务过程 → 声明粒度 → 确定维度 → 确定事实`，通过总线矩阵整合各业务数据，避免数据孤岛。

#### （1）总线矩阵
<img width="1662" height="630" alt="image" src="https://github.com/user-attachments/assets/470452ad-7a71-4dd6-99fc-120217a9450b" />

总线矩阵用于描述业务过程与公共维度的关联，是数仓结构规划的基础。每行代表业务过程，每列代表公共维度，通过标记（如“Y”）表示关联关系。

**示例（简化版）**：

| 业务过程         | 公共维度       | 时间 | 客户端 | 区域 | 用户 |
|------------------|----------------|------|--------|------|------|
| 发布/更新文章    | 每个文章发布1行 | Y    | Y      | Y    | Y    |
| 搜索行为         | 每个搜索行为1行 | Y    | Y      | N    | Y    |
| 点击事件         | 每个点击事件1行 | Y    | Y      | Y    | Y    |
| 新增专栏         | 每个专栏新增1行 | Y    | N      | N    | Y    |
| 用户注册         | 每个注册1行     | Y    | Y      | Y    | N    |

**维护规则**：新增业务流程或调整维度时，需增量更新总线矩阵。


#### （2）维度模式
优先采用星型模型（冗余数据提升OLAP查询性能），结合以下维度处理方法：

##### a) 代理键
- 适用场景：多源同一维度的维表整合（解决自然键不唯一问题）；
- 生成方式：使用Hive窗口函数`row_number()`生成唯一标识（如`row_number() over (order by natural_key) as surrogate_key`）。


##### b) 多层级维度
同一维度表存在多层级关系（如商品分类、区域），需扁平化处理（逆规范化）：

**示例（博客分类表）**：  
- 原表（`ods_blog_blog_channel`）：

| 字段名   | 数据类型 | 说明         |
|----------|----------|--------------|
| id       | bigint   | 主键         |
| name     | string   | 分类名称     |
| type     | bigint   | 分类类型     |
| parentid | bigint   | 父分类ID     |

- 扁平化后（`dwd_blog_blog_channel`）：

| 字段名       | 数据类型 | 说明           |
|--------------|----------|----------------|
| id           | bigint   | 主键           |
| name         | string   | 分类名称       |
| type         | bigint   | 分类类型       |
| parentid     | bigint   | 父分类ID       |
| parentname   | string   | 父分类名称     |
| parent_type  | bigint   | 父分类类型     |


##### c) 维度退化
简单维度无需单独建表，直接在事实表中保留编码或值（如订单状态`order_status`：1-待支付、2-已支付）。


##### d) 杂项维度
将多个简单维度通过`cross join`组合（如“终端类型+会员等级”组合为“终端-会员”杂项维度）。


##### e) 时间维度
构建统一时间维度表（`dim_pub_date`），整合多粒度时间信息，避免分析时直接使用SQL函数计算：

| 字段名        | 数据类型 | 说明                                                                 |
|---------------|----------|----------------------------------------------------------------------|
| day_dt        | date     | 日期（如2025-07-29）                                                 |
| year          | int      | 年份                                                                 |
| month_code    | string   | 月编码（如202507）                                                   |
| week_in_month | string   | 月度周（每月1-7日为week1，依次类推）                                 |
| xun_code      | string   | 旬编码（1-10日为xun1，11-20日为xun2，21-月末为xun3）                 |
| five_day_name | string   | 五日名称（1-5日为“第一个五日”，6-10日为“第二个五日”，最多6个）       |
| holiday       | string   | 节假日（如“元旦”“国庆”，非节假日为“无”）                             |
| w_insert_dt   | date     | ETL插入日期                                                          |

**使用示例**：订单表（`mall_orders_order_base`）新增时间代理键关联时间维度：

| 字段名        | 数据类型 | 说明                          |
|---------------|----------|-------------------------------|
| id            | bigint   | 订单主键                      |
| order_number  | string   | 订单编号                      |
| pay_time      | bigint   | 支付时间戳                    |
| pay_time_id   | int      | 关联时间维度表的代理键（FK）  |


##### f) 维度角色扮演
同一维度在事实表中多次出现时，通过视图区分角色：

**示例**：订单表同时包含支付时间和创建时间，需关联时间维度的两个视图：

| 字段名          | 数据类型 | 说明                          |
|-----------------|----------|-------------------------------|
| id              | bigint   | 订单主键                      |
| order_number    | string   | 订单编号                      |
| pay_time_id     | int      | 关联支付时间视图（`dim_pub_pay_date_view`） |
| create_time_id  | int      | 关联创建时间视图（`dim_pub_order_date_view`） |


##### g) 缓慢变化维度（SCD）
针对维度属性变化，采用以下处理方式：

| 处理方式 | 适用场景                                  | 实现方式                                                                 |
|----------|-------------------------------------------|--------------------------------------------------------------------------|
| 覆盖     | 无需保留历史值（如用户昵称）              | 直接用新值更新旧值                                                       |
| 新增行   | 需要追溯历史快照（如用户地址变更）        | 新增行记录，添加`start_date`（生效时间）、`end_date`（失效时间）、`is_valid`（是否有效）字段 |
| 新增列   | 需保留最近一次历史值（如商品最新价格）    | 新增`last_price`字段存储上一次价格，`current_price`存储当前价格           |


#### （3）表详细设计
输出表设计文档，包含维度表和事实表的详细信息：

- **维度表**：名称、描述、字段（名称/类型/说明）、SCD类型；
- **事实表**：外键（关联维度表）、退化维度、非规范化属性、度量值（可加/半可加/非可加）。

### 4. ETL流程设计与开发
ETL设计需明确任务流程、依赖、数据来源、分区策略等，遵循以下规范：


#### （1）SQL规范
| 项              | 说明                                                                 | 示例                                                                 |
|-----------------|----------------------------------------------------------------------|----------------------------------------------------------------------|
| 注释            | 新增关键逻辑注释（如业务背景、计算规则）                             | `-- 过滤测试订单：is_test=0表示正式订单`                             |
| `WITH AS`子句   | 替换多层子查询，提升可读性                                           | `WITH order_sum AS (SELECT order_id, SUM(amt) AS total FROM orders GROUP BY order_id) SELECT * FROM order_sum` |
| 简写            | 遵循度量术语表，同一维度名称统一                                     | 用`user_cnt`表示用户数，而非`u_num`                                  |
| 表别名          | 格式：`al_{表名简写}`，所有字段加别名前缀，避免字段冲突               | `SELECT al_ob.id, al_orb.refund_amt FROM ods_mall_orders_base al_ob JOIN ods_mall_refund_base al_orb ON al_ob.id = al_orb.order_id` |


#### （2）性能优化
| 优化点                 | 说明                                                                 |
|------------------------|----------------------------------------------------------------------|
| 谓词下推               | 将过滤条件写入`ON`子句，减少join数据量                               | `JOIN ... ON a.id = b.id AND b.status = 1`（而非先join再过滤）       |
| 避免全量排序           | 非必要时不使用`ORDER BY`，或限制排序条数（`LIMIT`）                  |                                                                      |
| Map Join               | 小表（<100万行）与大表join时使用，减少数据传输                       | `/*+ MAPJOIN(al_dim) */ SELECT * FROM al_big JOIN al_dim ON ...`     |
| 替代`count(distinct)`  | 用`count + GROUP BY`子查询避免数据倾斜                               | `SELECT COUNT(1) FROM (SELECT user_id FROM logs GROUP BY user_id)`   |
| 压缩格式               | 避免使用不可切分格式（如`gzip`），优先`ORC` `Parquet`                |                                                                      |
| 分区设计               | 大表增加二级分区（如时间+业务类型）                                  | `ods_mall_orders_{dt}_{biz_type}`（dt：日期，biz_type：业务类型）   |


#### （3）异常数据处理
| 处理方式       | 适用场景                                  | 说明                                                                 |
|----------------|-------------------------------------------|----------------------------------------------------------------------|
| 中断过程       | 核心数据异常（如订单金额为负）            | 触发告警，人工介入处理后重启任务                                     |
| 临时备份表     | 非核心异常（如个别字段为空）              | 将异常数据写入`err_ods_mall_orders`，后续单独处理                   |
| 审计字段标记   | 需要保留异常记录时                        | 新增`data_status`字段（0-正常，1-异常），并记录异常原因             |
